项目开始的时候，手上只有一份 Figma 文件和几个十六进制色值。两个月后，生产环境里跑着一套双主题设计系统，token 命名方案被我推翻重写了三次，也攒下了一些关于 Tailwind 在哪里开始帮倒忙的判断。

## 从错误的一端开始

第一个错误是急着挑颜色。我花了一个下午在 Tailwind 默认调色盘里比较 slate、zinc、neutral、stone，亮色暗色各试一遍。结果看起来不差，但完全是错的。

问题在于：我在定义关系之前就在选表面色。哪个元素叠在哪个上面？当背景从接近纯白翻转到接近纯黑，"primary"是什么意思？一条在亮色表面上显得微妙的边框，到了暗色背景上直接消失了怎么办？

我退回来，从层级关系开始。

## Token 层

CSS 自定义属性变成了整个系统的脊柱：

```css
:root {
  --bg-primary: theme('colors.stone.50');
  --bg-card: theme('colors.white');
  --text-primary: theme('colors.stone.900');
  --text-muted: theme('colors.stone.500');
  --border: theme('colors.stone.200');
  --accent: theme('colors.amber.600');
}

.dark {
  --bg-primary: theme('colors.zinc.950');
  --bg-card: theme('colors.zinc.900');
  --text-primary: theme('colors.zinc.100');
  --text-muted: theme('colors.zinc.400');
  --border: theme('colors.zinc.800');
  --accent: theme('colors.sky.400');
}
```

每个组件只引用 token，不碰原始颜色。`.dark` 一个声明翻转整个表面，Tailwind 的 `@theme` 把每个 token 映射成工具类。

这听起来像教科书。我没料到的是，中间态 token 出现的频率——`--bg-hover`、`--border-hover`、`--text-link-visited`——这些不在任何指南里。token 列表从 8 个长到 23 个才稳定下来。

## Tailwind 帮得上忙的地方

Tailwind 的工具类模型在设计系统里有三件事做得不错：

**间距一致性。** 当所有 margin 和 padding 都出自同一套比例尺，布局意外基本不再发生。看到 `p-4 gap-6` 就知道节奏，不用打开 DevTools。

**响应式断点。** `sm:`、`md:`、`lg:` 前缀让响应式逻辑跟元素待在一起，不用去另一个文件里找 media query。

**状态变体。** `hover:`、`focus-visible:`、`dark:` 在底层 token 正确的前提下组合得很干净。`bg-[var(--bg-card)] hover:bg-[var(--bg-hover)]` 读起来像一句话。

## Tailwind 跟你打架的地方

麻烦从需要表达 *token 之间的关系* 时开始。Tailwind 擅长施加值，但不是为计算值设计的。

我想让 `--bg-hover` 是"亮色模式下比 `--bg-card` 稍亮一点，暗色模式下也稍亮一点"。CSS `color-mix()` 可以直接做：

```css
--bg-hover: color-mix(in srgb, var(--bg-card) 92%, var(--text-primary));
```

但这是原始 CSS 自定义属性，Tailwind 不认识它，除非你在 `@theme` 里接上。于是你维护着两套并行系统——CSS 里的 token 定义和 Tailwind 配置里的工具映射——它们会慢慢走散。

我目前的折中方案：在一个 CSS 文件里定义所有 token，Tailwind 扩展一次消费它们，组件代码里永远不用 Tailwind 内置的颜色工具类（`bg-zinc-800`）。组件只看到语义名，比如 `bg-card` 或 `text-muted`。这行得通，但意味着我用 Tailwind 主要当间距和布局框架，不当颜色系统。

## 暗色模式的坑

`<html>` 上加 `class="dark"` 很简单，直到动画介入。主题切换要快到像瞬间发生，又不能快到闪烁。

我试过给每个自定义属性加 CSS transition。坏主意——同时 transition 23 个属性在中端手机上触发了布局抖动。最后的方案更粗暴：只 transition `body` 的 `background-color` 和 `color`，其他全部跳变。用户把背景切换感知为"转场本身"，不会注意到边框和阴影是瞬间跳的。

```css
body {
  transition: background-color 150ms ease, color 150ms ease;
}
```

有一个例外：`<html>` 在初始 HTML 里静态带着 `class="dark"`，避免 SSR 时闪一下错误主题。`next-themes` 负责运行时切换，但静态默认值烤进了构建产物。这意味着每个用户在 hydration 之前会看到一帧暗色模式——对于一个默认暗色的站点来说，可以接受。

## 组件边界

设计系统里最难的决策是在哪里画组件边界。一张卡片不是一个东西，它是一个表面、一种边框处理、一个 hover 状态、一个可选的头部区域，以及内容的间距规则。

我最终用了分层的方式：

```tsx
// 基础表面——只有视觉处理
<div className="bg-card rounded-xl border border-[var(--border)]
                hover:border-[var(--border-hover)] transition-colors">
  {children}
</div>

// 卡片容器——加上间距和交互行为
<div className="card-interactive p-6">
  {children}
</div>
```

`card-interactive` 是一个全局 CSS 类，承载了点阵纹理、hover 缩放和 focus ring。组件组合这些层，而不是各自重建。

好处：当我决定给所有可交互卡片加一层微妙的点阵背景时，改了一个 CSS 类，而不是编辑 14 个组件。

## 仍然不满意的地方

token 文件已经 87 行了，还在长。有些 token 存在只是因为某个组件在某个状态下需要一个略有不同的色阶。我怀疑 30% 可以用 `color-mix()` 从五个基础 token 推算出来，但我没做这次重构，因为现在的系统能用，我也怕在那些不再主动关注的组件里引入微妙的回归。

"设计系统"和"一堆碰巧保持一致的 token"之间的距离，比我预想的要小。真正的设计系统有文档、版本管理和给其他消费者的接入路径。我的只有一个 CSS 文件和脑子里的理解。对一个人的项目来说大概够了——如果有别人需要碰它，大概就不够了。
