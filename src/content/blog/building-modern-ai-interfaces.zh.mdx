> **范围说明**：下面的代码共享一套浏览器端状态机。API route、流协议、鉴权、重试和遥测是你自己的事。代码面向 Next.js 16 + React 19 的客户端组件，`/api/chat` 是一个同源 Route Handler，返回流式 `Response`。

我给一个内部工具做了一个聊天界面，后面接着 LLM 端点。第一版在演示里跑得很好。第二版在真实使用一周之后才算稳下来。区别不在模型——在于前端怎么处理流崩掉的时候。

## 最先崩掉的地方

第一版就是一个 `fetch` 调用、一个 `useState` 存响应文本、一个加载动画。一直到以下情况出现之前都没问题：

1. 用户在流式输出中途导航离开了。fetch 还在跑。state 更新打到了一个已卸载的组件上。
2. API 返回了 429。加载动画转到天荒地老。
3. 模型返回了空响应。UI 什么都不显示，也不给任何反馈。

这些都是无聊的问题。但它们恰好是让用户不信任一个 AI 功能的那些问题。一个卡住的聊天比一个说"出了点问题"的聊天更糟糕。

## 流式生成器

地基是一个异步生成器，chunk 到达时逐个 yield：

```typescript {5,8,12,28}
async function* streamResponse(prompt: string, signal: AbortSignal) {
  const response = await fetch('/api/chat', {
    method: 'POST',
    body: JSON.stringify({ prompt }),
    signal,
  });

  if (!response.ok) {
    throw new Error(`Chat request failed: ${response.status}`);
  }

  if (!response.body) {
    throw new Error('Chat response has no readable body');
  }

  const reader = response.body.getReader();
  const decoder = new TextDecoder();

  try {
    while (true) {
      const { done, value } = await reader.read();
      if (done) break;
      yield decoder.decode(value, { stream: true });
    }
    const trailing = decoder.decode();
    if (trailing) yield trailing;
  } finally {
    await reader.cancel().catch(() => undefined);
    reader.releaseLock();
  }
}
```

`signal` 参数是取消能工作的关键。用户按"停止"或导航离开时，abort controller 一下子拆掉 fetch、reader 和生成器。`finally` 块无论生成器怎么退出都会做清理。

末尾不带参数的 `decoder.decode()` 用来刷出 TextDecoder 内部缓冲区里残余的字节——这个细节在中日韩多字节文本里很重要。

## 状态机

不用 `isLoading` / `isError` / `hasData` 这些允许不可能组合的布尔值：

```typescript
type ChatState =
  | { status: 'idle' }
  | { status: 'streaming'; buffer: string }
  | { status: 'error'; error: Error; lastMessage: string }
  | { status: 'complete'; response: string };
```

四个状态。每个只有在那个状态下有意义的字段。你不能在 `streaming` 上访问 `error`。不能在 `complete` 上访问 `buffer`。UI 渲染函数对 `status` 做 `switch`，TypeScript 在每个分支里收窄。

这不是理论。`error` 上的 `lastMessage` 字段存在的原因是：流在句子中间断掉时，我需要展示断点之前已经到达的部分——用户想看到故障之前收到了什么，而不是一片空白。

## Hook

Hook 把生成器接到状态机上。棘手的部分是取消时的清理和防止过期闭包：

```tsx
import { useCallback, useReducer, useRef } from 'react';

type ChatAction =
  | { type: 'START' }
  | { type: 'CHUNK'; payload: string }
  | { type: 'COMPLETE' }
  | { type: 'ERROR'; payload: Error }
  | { type: 'CANCEL' };

function chatReducer(state: ChatState, action: ChatAction): ChatState {
  switch (action.type) {
    case 'START':
      return { status: 'streaming', buffer: '' };
    case 'CHUNK':
      return state.status === 'streaming'
        ? { status: 'streaming', buffer: state.buffer + action.payload }
        : state;
    case 'COMPLETE':
      return state.status === 'streaming'
        ? { status: 'complete', response: state.buffer }
        : state;
    case 'ERROR':
      return {
        status: 'error',
        error: action.payload,
        lastMessage: state.status === 'streaming' ? state.buffer : '',
      };
    case 'CANCEL':
      return { status: 'idle' };
  }
}

function useAIStream() {
  const [state, dispatch] = useReducer(chatReducer, { status: 'idle' });
  const abortRef = useRef<AbortController | null>(null);

  const send = useCallback(async (prompt: string) => {
    abortRef.current?.abort();
    abortRef.current = new AbortController();

    dispatch({ type: 'START' });
    const signal = abortRef.current.signal;

    try {
      for await (const chunk of streamResponse(prompt, signal)) {
        dispatch({ type: 'CHUNK', payload: chunk });
      }
      dispatch({ type: 'COMPLETE' });
    } catch (error) {
      if (error instanceof Error && error.name !== 'AbortError') {
        dispatch({ type: 'ERROR', payload: error });
      }
    } finally {
      if (abortRef.current?.signal === signal) {
        abortRef.current = null;
      }
    }
  }, []);

  const cancel = useCallback(() => {
    abortRef.current?.abort();
    dispatch({ type: 'CANCEL' });
  }, []);

  return { state, send, cancel };
}
```

`CHUNK` 的守卫（`state.status === 'streaming'`）防止迟到的 chunk 覆盖已完成或已出错的状态。catch 里的 `AbortError` 过滤防止用户主动取消被当作错误处理。`finally` 里的 `signal` 身份检查防止清理动作影响到已经开始的更新请求。

## 如果重来我会怎么做

从一开始就加 per-token 延迟追踪。首字节时间告诉你 API 的情况。token 间延迟告诉你流式实现的情况。当用户说"感觉很慢"的时候，你需要第二个数字来诊断问题到底在模型、网络还是渲染。

取消 UI 应该在 happy path 之前就搭好。"停止生成"不是锦上添花。用户一定会在流式输出中途离开页面，如果状态没有正确清理，下一次提交 prompt 就会跟一个僵尸生成器打架。

五件我不断提醒自己的事：

1. 第一天就上流式——后期改造流式非常痛苦。
2. 为失败而设计——每次 LLM 调用都可能超时、限流或胡说八道。
3. 按 token 测延迟，而不只看首字节时间。
4. 把取消写进契约——用户一定会在流式输出中途离开页面。
5. 给状态加类型——状态机从根上排除不可能的 UI 组合。
