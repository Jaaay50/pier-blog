I didn't start optimizing performance because I read an article about Core Web Vitals. I started because the hero section on my own site felt slow on my phone. The Galaxy background loaded, the particles converged, and the whole thing took long enough that I noticed it. Noticing it was the problem.

## Measuring Before Guessing

The instinct was to look at the WebGL pipeline. It's the most complex thing on the page, so it must be the bottleneck, right?

I ran Lighthouse on the deployed site instead. The results surprised me:

The three numbers that matter most:

| Metric | Target | What It Measures |
|--------|--------|------------------|
| LCP | < 2.5s | Visual completeness |
| INP | ≤ 200ms | Responsiveness to interaction |
| CLS | < 0.1 | Visual stability |

My initial Lighthouse run told a different story:

| Metric | Value | Rating |
|--------|-------|--------|
| LCP | 3.2s | Poor |
| INP | 280ms | Needs Improvement |
| CLS | 0.02 | Good |

LCP was 3.2 seconds. But LCP wasn't the particle animation — it was the hero image fallback. The browser identified the largest contentful paint as a background element that loaded after the WebGL canvas, because the canvas doesn't count as contentful paint until it has visible content.

The optimization I almost did (rewrite the particle system) would not have moved LCP at all.

## Fixing What Actually Mattered

### LCP: The Hero Image

The fix was mechanical: preload the critical image, use the `priority` flag, and provide a blur placeholder:

```tsx
<Image
  src={hero}
  alt="Hero"
  priority
  sizes="(max-width: 768px) 100vw, 50vw"
  placeholder="blur"
/>
```

After this, LCP dropped to 1.8s on a 4G throttle. The particle system had nothing to do with it.

The lesson: measure before assuming. The most complex code on the page is not always the bottleneck. The browser's definition of "largest contentful paint" doesn't care about your WebGL.

### INP: The Event Handler Problem

INP only showed up as a problem on mobile. On desktop, every interaction responded in under 50ms. On a mid-range Android phone, tapping the theme toggle took 280ms.

The cause: the toggle handler triggered a class change on `<html>`, which forced a repaint of every element with a CSS transition on a custom property. 23 custom properties were transitioning simultaneously.

```css
/* Before: everything transitions */
* {
  transition: all 150ms ease;
}

/* After: only the properties that users perceive */
body {
  transition: background-color 150ms ease, color 150ms ease;
}
```

Reducing the transition scope dropped INP to under 120ms on the same device. Everything else — borders, shadows, accent colors — snaps instantly, and users don't notice.

### CLS: Already Fine, Almost Ruined It

CLS was 0.02, well within the "good" threshold. Then I added a dynamic font loading strategy and watched it jump to 0.18.

The problem: `font-display: swap` causes a layout shift when the web font arrives and glyphs change size. For CJK fonts, the shift is larger because the character width difference between the fallback and the web font is bigger.

```css
@font-face {
  font-family: var(--font-display);
  font-display: optional;
  size-adjust: 100%;
}
```

`font-display: optional` eliminates the swap — if the font hasn't loaded by the time the browser needs it, it stays on the fallback for that page load. CLS went back to 0.02. The tradeoff: users on slow connections see the fallback font for the entire first visit. For a site where the content is code and prose, not a brand-sensitive landing page, I'm fine with that.

## Code Splitting: The Easy Win I Almost Over-Did

Next.js App Router handles route-level code splitting automatically. Every route is a separate bundle. The temptation is to then `dynamic()` import everything else:

```typescript
import dynamic from 'next/dynamic';

const Chart = dynamic(() => import('@/components/Chart'), {
  loading: () => <ChartSkeleton />,
  ssr: false,
});
```

This is correct for heavy components that aren't needed on first render — WebGL demos, code editors, visualization widgets. It's wrong for components that are part of the critical rendering path. A dynamically imported hero section defeats the purpose of SSG.

The rule I follow: `dynamic()` for below-fold interactive components. Static imports for everything in the initial viewport.

## Measuring in Production

The build log is the first diagnostic:

```bash
npm run build
# Route size and First Load JS are printed per route
```

For runtime data, the web-vitals hook:

```tsx
'use client';

import { useReportWebVitals } from 'next/web-vitals';

export function WebVitals() {
  useReportWebVitals((metric) => {
    console.log(metric.name, metric.value, metric.rating);
  });
  return null;
}
```

This logs metrics to the console. Sending them to an endpoint requires authentication, retention, sampling, and an actual `/api/vitals` handler — work I haven't done yet because console logging during manual testing catches the problems I can act on.

## What I Took Away

1. Measure first. The bottleneck is usually not where you think it is.
2. LCP is almost always an image problem. Optimize the hero image pipeline before touching JavaScript.
3. INP shows up on phones, not laptops. Test on a real mid-range device or throttle aggressively.
4. CLS is easy to maintain and easy to break. Font loading and dynamic content are the usual culprits.
5. Bundle size is a feature. Treat it like memory usage — track it, budget it, and notice when it grows.
