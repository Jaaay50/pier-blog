我在把一个仪表盘从 Pages Router 迁移到 App Router 时注意到一件奇怪的事：状态管理层——一个有六个 slice 的 Zustand store、三个 Context provider、再加一把自定义 hook——几乎没什么事可做了。不是因为我换了别的方案，而是框架悄悄地吸收了它管理的大部分东西。

那次迁移是我对 2025 年状态管理的看法真正成形的地方。不是来自读文档。

## 消失的部分

旧应用有一个 `useCurrentUser` hook，背后是一个 Context provider。它在 mount 时调 API route，把结果缓存在 state 里，然后往下传。每个需要鉴权的页面都导入它。

在 App Router 里，同样的数据是 Server Component 里的一个 `fetch` 调用。没有 hook，没有 provider，不影响客户端打包体积。用户对象存在于服务端，序列化进 HTML，到达浏览器时已经渲染完毕。

```tsx
async function UserProfile({ id }: { id: string }) {
  const user = await db.user.findUnique({ where: { id } });
  if (!user) return <p>找不到用户。</p>;

  return (
    <div>
      <h1>{user.name}</h1>
      <p>{user.bio}</p>
    </div>
  );
}
```

没有 `useEffect`。没有 loading 状态。没有缓存失效 hook。这个组件甚至不会发出 JavaScript。

我在代码库里过了一遍，到处都是同样的模式：过滤器状态可以是 URL 参数，表单状态可以是 `useActionState`，权限检查可以在服务端、在组件树开始渲染之前就完成。

## 一个经得住的分类法

在引入任何库之前，我现在只问一个问题：这段状态归谁？

```
服务端数据？               → RSC + fetch
在 URL 里？               → useSearchParams
表单？                    → useActionState
只属于一个组件？           → useState
跨 3 个以上不相邻的客户端组件？ → Zustand
```

令我意外的是最后一行用得多么少。在整个仪表盘迁移里，只有两处状态需要 Zustand：侧边栏的展开/收起（因为 layout、导航和键盘快捷键处理都要读它）和一个通知队列（因为 toast 可能从任何地方触发）。

其他的全都归进了前四类。

## URL 状态被严重低估了

过滤器页面教会了我这一点。旧版本把 `sort`、`status`、`dateRange` 存在 Zustand slice 里。要分享一个过滤后的视图得手动把状态拼进 URL。浏览器后退会丢掉过滤。刷新也会丢。

把过滤器移到 `useSearchParams` 之后，这些全免费解决了：

```tsx
'use client';

import { useSearchParams, useRouter } from 'next/navigation';

function Filters() {
  const searchParams = useSearchParams();
  const router = useRouter();

  const setFilter = (key: string, value: string) => {
    const params = new URLSearchParams(searchParams.toString());
    params.set(key, value);
    router.push(`?${params.toString()}`);
  };

  return (
    <select
      value={searchParams.get('sort') || 'newest'}
      onChange={(e) => setFilter('sort', e.target.value)}
    >
      <option value="newest">最新</option>
      <option value="popular">热门</option>
    </select>
  );
}
```

URL 可分享。浏览器历史正常工作。刷新后状态还在。兼容 SSR。不需要任何库。

代价：每次过滤变化都触发一次导航，在 App Router 里意味着一次服务端请求。如果是静态页走 CDN 命中，很快。如果页面有重型服务端计算，可能需要 `router.replace` 配合 `scroll: false`，或者对参数做 debounce。

## Zustand 真正有用的场景

侧边栏切换是典型案例。三个不相邻的组件需要读它：侧边栏本身、主内容区（宽度变化）和一个键盘快捷键处理器。它们之间没有父子关系。用 `useState` 就得提升到 layout 根节点，到那一步你其实造了个更差的 Context provider。

```typescript
import { create } from 'zustand';
import { persist } from 'zustand/middleware';

interface AppStore {
  sidebarOpen: boolean;
  toggleSidebar: () => void;
}

export const useAppStore = create<AppStore>()(
  persist(
    (set) => ({
      sidebarOpen: true,
      toggleSidebar: () => set((s) => ({
        sidebarOpen: !s.sidebarOpen
      })),
    }),
    { name: 'app-store' }
  )
);
```

不需要 Provider。selector 限制重渲染。`persist` 跨 session 记住状态。这就是 Zustand 那 3KB 真正值得的范围。

如果状态没有跨到 3 个以上不相关的组件，`useState` 就够了。这不是极简主义——就是用对了工具。

## 反复出现的反模式

```typescript
// ❌ 一个布尔值搞出三个文件加一个 provider
const ThemeContext = createContext();
const ThemeProvider = ({ children }) => { /* ... */ };
const useTheme = () => useContext(ThemeContext);

// ✅ 一行搞定，无 provider，精准重渲染
const useTheme = create((set) => ({
  theme: 'dark',
  toggle: () => set(s => ({ theme: s.theme === 'dark' ? 'light' : 'dark' }))
}));
```

Context 有正当用途——依赖注入、主题嵌套、复合组件 API。但对于多个叶子组件需要读取而不应该重渲染父节点的全局状态来说，它的形状不对。每次 Context 更新都会重渲染每个消费者，即使它们读的那个值没变。Zustand 的 selector 模型避开了这个问题。

## 这次迁移教会我的事

最大的收获跟库没关系，是关于分类。大部分状态管理的痛苦来自于把客户端状态放在了本该用服务端状态、URL 状态或表单状态的地方。

Server Components 没有消灭状态管理。它消灭的是那一类状态管理——本来就是对"没有直接数据访问的服务端渲染"的变通方案。剩下的状态——UI 开关、跨组件协调、客户端缓存——是真正的客户端工作，而且它是一个更小的问题。

五件我不断提醒自己的事：

1. Server Components 消灭了大部分客户端状态。让平台去干活。
2. URL 状态是免费的。过滤器、分页、弹窗——放进 URL。
3. `useState` 被严重低估。大部分 UI 状态本来就是局部的。
4. 剩下的交给 Zustand。API 极简，手感最好。
5. 最好的状态管理是没有状态管理。能推导就不要存储。
